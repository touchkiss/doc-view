# YApi MCP Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a local Streamable HTTP MCP server to the IntelliJ plugin so an Agent can locate Java Controllers by fully qualified class or method reference and create or update their API documentation in YApi.

**Architecture:** Register one application-level MCP server in the plugin. The server exposes `upload_yapi_api_doc(projectPath, reference)`, routes `projectPath` to an already-open IntelliJ Project, and delegates PSI resolution, `DocView` generation, and YApi upsert work to focused services. The server binds only to `127.0.0.1` and has no MCP authentication token.

**Tech Stack:** Java 25, IntelliJ Platform SDK 2026.2 APIs already used by the plugin, Gradle, official MCP Java SDK Streamable HTTP transport, Gson/YApi DTOs, JUnit 4.

## Global Constraints

- MCP transport is Streamable HTTP; legacy HTTP+SSE is not a primary transport.
- The MCP server listens only on `127.0.0.1` and has no MCP Token or authentication header.
- `projectPath` must identify an already-open IntelliJ Project; the server must never open arbitrary directories.
- YApi URL, project ID, and YApi token are read only from the target project's `YApiSettings`.
- A class reference uploads all supported API methods; `Class#method` uploads only that method.
- Existing YApi interfaces are updated by `HTTP method + path`; missing interfaces are created.
- Batch uploads continue after an individual method failure and return per-method results.
- PSI access runs under IntelliJ read actions; network calls must not block the EDT.
- Existing UI upload flows must continue to work.
- Do not include unrelated untracked workspace files in commits.
